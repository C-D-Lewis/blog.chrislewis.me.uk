Today I finally got to releasing the first version of Dashboard 2 - the
successor to one of my most popular apps back in 2016 called
[Dashboard](https://apps.rebble.io/en_US/application/53ec8d840c3036447e000109)
which allowed toggling things like WiFi and mobile data on or off, viewing phone
battery level and connected networks, activating a loud sound to help find the
phone, lock the phone, and much more.

![](assets/media/2026/08/dashboard1.jpg)

Sadly in the years since, security changes, API deprecations, background app
execution restrictions, minimum Android API requirements and Play Store red tape
have all conspired to kill the original app.

It can still be sideloaded and installed by bypassing several Android checks and
features (as far as I'm aware) but the code is old (Java!), complicated, and the
majority of the features won't work on modern Android platforms, which are
fairly strictly required. Interested parties can still find the
[source code](https://github.com/C-D-Lewis/pebble-dev/tree/master/watchapps/dashboard)
on GitHub.

## A Modern Alternative

With the resurrection of Pebble, new devices, and now a new version of
[PebbleKit Android 2](https://github.com/pebble-dev/PebbleKitAndroid2)
available, it became possible to either update the existing app or create a new
one for the modern Android and Pebble landscape. It seemed sad to rip out most
of the existing app's UI, features, plumbing etc and try and squeeze the old
Java codebase into modern Android Studio, so I opted to create something new.

Sadly, job and personal commitments meant that development was slow to start and
progressed at a snail's pace, but after doing plenty of experimentation and
diving deep into Kotlin and Jetpack Compose UI, I finally arrived at something
that contained at least a few bits of phone data and a couple of useful
actionable features:

- Device name

- Battery level (and charging status)

- Free storage space

- Next Android alarm time

- Find Phone with loud sound

- Cycle ringer modes (requires additional permission grant)

More features should hopefully come after, but I wanted to draw the line
somewhere or the first version would never get released. I have created a
[GitHub Issue](https://github.com/C-D-Lewis/pebble-dev/issues/18) to track
future features and feature requests. As expected, some are impossible nowadays,
or require special access or workarounds such as
[Shizuku](https://shizuku.rikka.app/) which I am hesitent to rely upon too
strongly.

So, what does it look like? Quite similar and yet different. Since there are
more items of data available than actionable toggles/tools (not settled on the
correct term yet), it made sense to make the primary UI focused on data, and
pull down the toggles instead of the reverse as the old app had it.

![](assets/media/2026/08/dashboard2-sbs.jpg)

The toggles slide into view when the Up button is pressed and retracts when
it is pressed again and the first toggle is selected. Pressing Select will
activate a toggle (or currently do nothing if the feature requires additional
permissions, a better UX for this is on the TODO list).

The Android app UI is similarly as simple, since mostly all it has to do is
listen to and response to messages when the screen is off. It contains
information as well the the opportunity to grant additional required permissions
if the user wants to enable them.

![](assets/media/2026/08/dashboard2-android.png)

Currently the Android app is installed from a link to S3, or from source code.
I have no appetite to get back into the Google Play Store web of policies and
red tape...

## Into the Weeds

This time around, I wanted to keep the UI and communication protocol as simple
to maintain and extend as possible. This means that it should be relatively
easy to add new features and data sources without too much work, or to remove
them if they are killed by Google (there is precedent!).

When the app launches, it sends an <code>AppMessage</code> to the phone with
the expected protocol version (a simple integer this time around instead of
re-implementing semver) and the phone assembles the response as a dictionary
of data items and the compatible protocol version. If there is a mis-match,
an error is displayed and the user needs to check either of both of the watchapp
and Android companion app are up to date. This single response has all the data
required so the sync is nice and fast and extensible.

```text
/**
 * Respond to a sync request with current state.
 */
suspend fun handleSyncRequest(): ReceiveResult {
    // Assemble all sync data
    val dict = mapOf(
        Constants.MESSAGE_KEY_COMPAT_PROTOCOL_VERSION to PebbleDictionaryItem.Int32(Constants.COMPATIBLE_PROTOCOL_VERSION),
        Constants.MESSAGE_KEY_SYNC_TOGGLE_ORDER to PebbleDictionaryItem.Text(getToggleOrderString(this)),
        Constants.MESSAGE_KEY_SYNC_DEVICE_NAME to PebbleDictionaryItem.Text(Device.getDeviceName(this)),
        Constants.MESSAGE_KEY_SYNC_BATTERY_PERC to PebbleDictionaryItem.Text(Battery.getBatteryLevel(this).toString()),
        Constants.MESSAGE_KEY_SYNC_FREE_SPACE to PebbleDictionaryItem.Text(Device.getFreeDiskSpace()),
        Constants.MESSAGE_KEY_SYNC_FREE_SPACE_PERC to PebbleDictionaryItem.Text(Device.getFreeDiskSpacePercentage().toString()),
        Constants.MESSAGE_KEY_SYNC_NEXT_ALARM to PebbleDictionaryItem.Text(Alarms.getNextAlarmTime(this)),
        Constants.MESSAGE_KEY_SYNC_IS_CHARGING to PebbleDictionaryItem.Int32(if (Battery.isCharging(this)) 1 else 0),
    )

    val result = sender.sendDataToPebble(Constants.APP_UUID, dict)
    Log.d(TAG, "Send $dict: $result")
    return ReceiveResult.Ack
}
```

As before, the current state of toggles takes the form of a single
<code>AppMessage</code> tuple as a string. The format is <code>xy</code> for
each toggle that exists, where <code>x</code> is an integer signifying the
toggle type, and <code>y</code> represents the state. States can include 'on',
'off', 'loud', 'vibrate', 'silent' and more in the future. For example, with
Find Phone off and the ringer set to loud:

```text
0112
```

Every response to actioning a toggle includes this tuple, so the state is always
reflected on the watch automatically after each action. Unfortunately with my
curreny Kotlin level of experience (just this project!) this string construction
is very verbose...

```text
/**
 * Get toggle order as a string. Constructed based on current state.
 *
 * Format: 2 chars per toggle - [TYPE,STATE] with defined toggle types and state values.
 */
fun getToggleOrderString(context: Context): String {
    return "${Constants.TOGGLE_TYPE_FIND_PHONE}" + (if (FindPhone.isPlaying()) Constants.TOGGLE_STATE_ON else Constants.TOGGLE_STATE_OFF) +
            "${Constants.TOGGLE_TYPE_CYCLE_RINGER}" + Ringer.getRingerModeProtocolValue(context)
}
```

Perhaps there is a better way I can discover in the future...

## Conclusion

That's pretty much all there is to this MVP version of Dashboard 2! The ball is
rolling, the initial version is out, and hopefully in future I can restore a few
more of the old features, check out Shizuku, or explore new capabilities such as
summoning other Android apps or activities. How about a toggle that launches the
Google Pay app for the next time you unlock your phone? Something to save some
time.

As usual, the
[source code](https://github.com/C-D-Lewis/pebble-dev/tree/master/watchapps/dashboard2)
is available and documented to a basic level - and if any more competent Android
developers feel they can add useful new items of data or toggles, PRs are
welcome!

For the near future, some items include:

- More UI polish on both sides, such as handling missing permissions.

- A scroll view for the data list to allow many more items.

- Fewer disparate enums/constants/places to add new data or features.

- Driving the data list and toggle pane based on the received protocol string, potentially allowing Android-only changes to be made (aside from showing strings and icons on the Pebble side).

So,

and let me know what you think in the
